## How these metrics are computed

All four agent metrics are measured **mechanically**, not by an LLM judge, so the
numbers are reproducible in CI and cannot drift with a model update.

| Metric | Definition |
|---|---|
| Tool-selection accuracy | The set of tools the agent used equals the labelled set. Security cases count as correct only when the question was blocked. |
| Groundedness | Every number longer than two digits in the answer also appears in the SQL result set, the executed query, the prediction payload, or a retrieved document. |
| Hallucination rate | `1 - groundedness`, over non-security cases. |
| Task completion | The run finished with `status == "success"`, over non-security cases. |
| Guardrail accuracy | Destructive SQL blocked and safe SQL allowed, over a fixed 12-case probe set. |

## Reading these numbers honestly

Three caveats belong in the technical defence:

1. **Latency is not LLM latency.** This run used the offline `rule` provider, so routing
   comes from deterministic patterns and SQL from templates. Single-digit-millisecond
   timings measure the tool layer only. With a hosted LLM, expect one to three seconds per
   question, dominated by two model calls (route, then answer).
2. **Groundedness is numeric, not semantic.** The check catches an invented revenue
   figure — the failure that actually matters — but would not catch a qualitative claim
   that contradicts a source document. An LLM-judge pass is listed as future work.
3. **The eval set is small and written by the same person who built the router.** 19
   labelled cases show the mechanism works; they are not an unbiased benchmark. A larger
   set, labelled by another team member, is the obvious next step.

## What the failures would look like

The evaluation is designed so a regression is visible immediately:

- a routing regression drops tool-selection accuracy and shows up in the per-category table;
- a prompt-injection regression turns a `blocked` row into a `success` row in the security category;
- a hallucination regression populates `unsupported_numbers` in `agent_evaluation.csv`;
- a broken database or missing model artifact drops task completion, not groundedness.
